## 02. 서비스 목표 및 사용자 시나리오

사용자는 생활체육 시설을 찾고, 자신의 종목·지역·실력·성별 조건에 맞는 운동 모임을 검색하고 참여한다. 자연어로 조건을 입력하면 AI가 검색 조건/매치 개설 초안을 제공하지만, 저장 및 최종 참여 허용은 서버가 검증한다.

- 시나리오 A: 시설 검색 → 상세·예약 URL 확인 → 시설에 연결된 매치 개설 → 다른 사용자의 참여.
- 시나리오 B: 자연어 매치 검색 → 조건 요약 확인·직접 수정 → 기존 매치 상세/참여.
- 시나리오 C: 로그인 사용자 관심 종목·지역·성별 기반 맞춤 추천(최대 3개).
- 운영 시나리오 D: Match 이벤트 Kafka 게시 → AI 조회 모델 갱신 → Grafana로 오류율/응답시간 확인.

## 04. 2차 MSA 필수 요구사항(10개 · 각 7점)

공식 2차 안내는 3~4개 이상 서비스, Eureka, Gateway, Config, OpenFeign, Kafka, 도메인 API, Database per Service, Docker/Compose, 차별화 핵심 기술 1개를 요구한다. 10번 기술로 모니터링을 우선 제안하되 팀 합의가 필요하다.


### MSA-01  4개 비즈니스 서비스 책임 분리

Identity/Facility/Match/AI 서비스 각 독립 프로세스, 도메인 소유권·API 경계 구분.


| 인수 기준  4개 서비스 각각 빌드/기동, 타 서비스 DB 직접 조회·공유 엔티티 금지. |
| --- |


### MSA-02  Eureka 등록

4개 비즈니스 서비스, Gateway 등 관리 대상 서비스 등록/상태 확인.


| 인수 기준  Eureka UI에서 서비스 등록/UP, 중단 시 변화 확인. |
| --- |


### MSA-03  단일 진입점

Gateway 라우팅 /api/users,/api/auth,/api/profiles,/api/matches,/api/services,/api/ai 및 공통 요청 로그/인증 헤더 검증.


| 인수 기준  프론트는 Gateway만 호출, 라우트 6개 구간 정상, 비공개 /internal 외부 차단. |
| --- |


### MSA-04  Config Server 설정 중앙화

서비스별 local/dev/prod 설정 Config Server, 보안 값은 환경변수 주입.


| 인수 기준  Config Server 프로필 조회·설정 반영 증빙, 저장소 비밀값 미노출. |
| --- |


### MSA-05  동기 서비스 조회

Match→Facility 시설 검증, AI→Identity 추천 프로필 조회, AI→Match 검색을 Feign으로 호출.


| 인수 기준  타 서비스 DB 직접 접근 없음; 정상/404/타임아웃 경계 검증. |
| --- |


### MSA-06  비동기 이벤트 동기화

Match에서 생성·참가·탈퇴·삭제 이벤트 발행; AI가 추천 조회 모델 반영.


| 인수 기준  Kafka publish/consume 증빙, 중복 수신 시 중복 반영 없음, 실패 재처리 경로. |
| --- |


### MSA-07  기존 핵심 CRUD·상태 유지

기존 21개 API 외부 경로 최대한 유지, 생성/참여/취소/탈퇴 등 상태 검증.


| 인수 기준  기존 프론트 핵심 시나리오 Gate 통과, 400/401/403/404/409 증빙. |
| --- |


### MSA-08  Database per Service

4개 논리 DB/스키마와 계정 분리, Match의 외부 service_id/user_id를 식별자 참조만 유지.


| 인수 기준  ERD 4개, cross-schema FK 0, 서비스별 DB 접속 계정 권한 분리. |
| --- |


### MSA-09  Dockerfile·Compose 통합

4개 애플리케이션 + Eureka/Gateway/Config + Kafka + MariaDB/Redis를 Docker Compose로 통합.


| 인수 기준  docker compose up --build 성공; health 검증; 종료/재기동 데이터 유지. |
| --- |


### MSA-10  모니터링 채택

Micrometer/Prometheus/Grafana로 전체 서비스 지표와 장애 시 응답·오류 변화 관측.


| 인수 기준  대시보드 캡처, 요청량/오류율/응답시간/서비스 상태 시연. |

## 06. 선택 요구사항(P2) 및 비배점 개선 제안

ENH-01~04는 공식 선택요구사항(조건 충족 시 각 3점) 후보이며, ENH-05 Outbox는 구현 완성도 향상을 위한 내부 개선안으로 별도 배점이 없다.


| ID | 후보 | 목표 / 수용 기준 |

## 09. 원본 대비 불일치 및 승인할 결정

D-01  매치 목록 API  공개 API는 GET /api/matches 유지; /search 별도 추가하지 않음  [확정 제안]

D-02  PK 데이터 타입  BIGINT 기준. 원본 ERD는 설명용으로만 사용  [확정 제안]

D-03  시설 예약  직접 예약/결제 기능은 범위 밖. 외부 예약 링크 제공  [확인]

D-04  DB 분리  match.service_id,participant.user_id는 타 DB ID 참조만; cross-DB FK 금지  [2차 제안]

D-05  정원/상태  회원 이탈/정원 변경/동시 참여 시 원자 처리 유지  [2차 제안]

D-06  차별화 기술  모니터링(Micrometer/Prometheus/Grafana) 우선 제안; 팀 확정 필요  [승인 필요]

D-07  버전 호환성  Spring Cloud 2025.0.x 계열 BOM 사용, 부트 3.5.x 버전 조합 실제 빌드 검증  [확인 필요]

D-08  데이터 샘플  기존 DB 시드 및 Mock으로 필수 E2E 재현; 실제 API 키는 팀 준비  [확인 필요]

D-09  API 오류 형식  2차 Gateway 전면 오류 표준화는 선택적; 기존 FE 호환 우선  [승인 필요]

D-10  테스트 상태  2차 신규 테스트는 전부 Not Run; 실제 재실행 후만 Pass  [확정]
